# AI 板块提示词设计说明（AI 学习日课 / 本周技术速递）

> 对应文件：`src/server/llm/prompts/ai-course.ts`、`src/server/llm/prompts/ai-weekly.ts`
> 自检脚本：`src/server/llm/prompts/_check-ai.ts`（运行：`npx tsx src/server/llm/prompts/_check-ai.ts`）
> 输出契约：`src/server/llm/schema.ts` 里的 `CoursePayloadSchema` / `WeeklyPayloadSchema`

---

## 一、两个提示词各是什么

| 板块 | id | 频率 | 一篇讲什么 | 长度基准 |
|---|---|---|---|---|
| AI 学习日课 | `ai-course` | 每天 1 篇，按课程大纲推进 | 一个大模型底层机制 | body 1100–1600 字 |
| 本周技术速递 | `ai-weekly` | 每周 1 篇 | 这一周 AI 技术上发生了什么，为什么重要，和你有什么关系 | body 900–1400 字 |

两个板块的读者是同一个人：**会用大模型 API、但不懂底层原理的工程师**。他会写代码、会发请求、会处理报错，缺的是「模型内部到底在干什么」这一层解释。

## 二、ai-course（AI 学习日课）

### 2.1 设计理由

1. **读者定位决定内容边界。** 系统提示词里写死了「禁止讲『怎么用网页版』『怎么写提示词』这类他已经会的东西」。读者每天在调 API，再讲一遍 API 用法就是浪费他的一天。所有内容收敛到一句话：**这件事在底层到底是怎么发生的**。
2. **锚点机制是这一板块的支点。** 每一讲都带一个 `lesson.anchor`（读者写过的那段调用场景）。提示词强制要求正文里必须有且只有一段，把本讲机制挂到这个锚点上——机制要对应到请求、参数、返回里的具体位置，让读者能对上自己写过的代码。少了这一段，这一讲就退化成通用科普。
3. **先直觉后机制。** 顺序被规定为：现象 → 大白话直觉 → 底层机制 → 术语解释 → 公式或伪代码加一句人话 → 锚点场景对照 → 与本周动态的关联 → 边界与不确定性 → 收束。术语第一次出现必须紧跟一句大白话解释；公式或伪代码后面必须紧跟一句人话解释。这两条是给「不懂原理」的读者兜底的。
4. **本周动态是钩子，不是内容来源。** `latestContext` 里的条目只能被「挂靠」：至少挑一条做例子，并把用了哪条写进 `meta.latestTieIn`；没有可用动态时，必须原样写「本周无直接关联，用常见工程场景举例」，不许拿一条无关新闻硬拗。这样每周课既有「今天」的实感，又不会为了凑动态而编造。
5. **事实纪律分层。** 除输入里出现过的模型名与版本号外不写具体模型名；所有推断要用「通常 / 大致 / 一般来说 / 值得注意的是 / 取决于」这类措辞点明。对原理课来说，这是防止「听起来很对但其实没根据」的最好手段。
6. **练习必须可执行。** `meta.exercise` 落地 `lesson.exercise` 的意图，但必须同时满足：十分钟内能做完、结果自己能验证、验证方式写得清楚（看什么输出、什么数值、什么现象算通过）。
7. **长度给得比其它板块宽。** 原理课要讲透，body 放宽到 1100–1600 字（其它板块是 900–1500），script 放宽到 450–800 字（其它板块 400–700）。

### 2.2 字段要求

顶层字段（与其它板块共用 `BasePayloadSchema`）：

| 字段 | 类型 | 要求 |
|---|---|---|
| title | string | 一句话标题，不超过 25 字 |
| subtitle | string | 一句话副标题，不超过 40 字 |
| summary | string | 120–200 字 |
| takeaways | string[] | 3–5 条，每条 20–45 字，一句话，不写序号 |
| body | string | 1100–1600 字，段落用空行分隔，可用两个星号做粗体，不写 Markdown 标题 |
| script | string | 450–800 字，口语化，可直接朗读 |

meta 字段（清单由 zod 契约推导，提示词自动跟着契约走）：

| 字段 | 要求 |
|---|---|
| lessonNo | 本讲编号，与输入一致 |
| stage | 阶段代号，与输入一致 |
| stageTitle | 阶段名称，与输入一致 |
| anchor | 一句话写清本讲机制在锚点场景的哪一步起作用 |
| exercise | 十分钟内能做完、能自己验证的练习，写清步骤与验收方式 |
| keywords | 三到六个本讲真正讲到的术语，每个都要在正文里出现过 |
| latestTieIn | 写明用了本周哪一条动态（标题与来源）以及它和本讲的关系；没有可用动态就原样写「本周无直接关联，用常见工程场景举例」 |

> **实现说明**：`【输出结构】` 里的 meta 字段清单不是手写的，而是从 `CoursePayloadSchema.shape.meta.shape` 取出来的（`ai-course.ts` 里的 `courseMetaFields`）。契约新增或改名字段时，提示词自动同步，不会出现「提示词要一套字段、契约要另一套」。

## 三、ai-weekly（本周技术速递）

### 3.1 设计理由

1. **它不是新闻摘抄，是一份技术周报。** 读者不缺新闻，缺的是判断。提示词给了一条主线要求：每周只有一个主线判断，不写成流水账；每条都必须落到「对每天调 API 的人意味着什么」。
2. **四段式要点结构。** `whatChanged` 只写事实（技术层面到底变了什么），`whyItMatters` 写机制层面的影响，`impactOnYou` 写具体动作或选型判断（怎么改用法、要不要换模型、要不要加缓存、要不要改评测方式、什么场景可以先不跟）。事实与解读分开，避免「听起来很专业的形容词」。
3. **热度不等于进展。** 提示词明令不得把「开源项目变多」「星标涨得快」说成「技术突破」。仓库部分只描述输入里给出的信息（做什么用的、什么语言、多少星），不得推断成熟度、性能或采用情况。
4. **source / url 必须能对上。** 只有在输入里能一一对应上时才填；对应不上就留空字符串，不许拼一个像模像样的链接——页面上的引用必须点得开且对得上。
5. **术语一律翻译成人话。** `meta.techList` 每条术语配一句「说白了就是……」的解释。
6. **语气克制。** 禁用「震撼 / 颠覆 / 炸裂 / 碾压 / 史上最强」这类营销词；该夸讲清楚好在哪，该疑讲清楚疑在哪。

### 3.2 字段要求

顶层字段与其它板块一致，body 放宽为 900–1400 字、script 为 400–700 字。

meta 字段：

| 字段 | 要求 |
|---|---|
| weekKey | 与输入的周次一字不差 |
| period | 与输入的覆盖区间一字不差 |
| highlights | 3–6 条，每条含 whatChanged / whyItMatters / impactOnYou，另有 source、url（对不上就留空） |
| techList | 2–5 个术语，每条含 term 与大白话解释 |

> **实现说明**：`【输出结构】` 里的字段清单同样从 `WeeklyPayloadSchema` 推导（`ai-weekly.ts` 里的 `weeklyMetaFields` / `highlightFields` / `techFields`）。数组元素若被 zod 的 transform 包成管道类型，会自动拆到管道内侧取字段，不会渲染成空对象。

## 四、如何判断生成结果不合格

### A. 格式不合格（机器可判）

1. 输出被三个反引号代码块包裹，或 JSON 前后有解释文字、前言、结语。
2. 字段与契约不一致：多了字段、少了字段、改了字段名。
3. `JSON.parse` 解析失败：尾随逗号、单引号、注释、`NaN`/`Infinity`、字符串里有真实换行。
4. 字段类型不对：需要数字的地方给了字符串，需要数组的地方给了字符串。

### B. 日课内容不合格

5. 出现「怎么用网页版」「怎么写提示词」「怎么注册账号」这类读者已经会的内容。
6. 术语第一次出现没有紧跟一句大白话解释。
7. 公式或伪代码后面没有紧跟一句人话解释。
8. 没有锚点对照段，或者锚点段写成了「这很重要」这种空话。
9. 一讲里塞了多个机制，写成了目录。
10. `meta.exercise` 十分钟做不完、没法自己验证、或者没写验收方式（看什么输出算通过）。
11. `meta.latestTieIn` 没有引用本周动态里的具体条目；或者有可用动态却写「本周无直接关联，用常见工程场景举例」。
12. `meta.keywords` 里的术语在正文里根本没出现过。
13. 长度越界：summary 不在 120–200、takeaways 不在 3–5 条或单条不在 20–45 字、body 不在 1100–1600、script 不在 450–800。

### C. 周报内容不合格

14. `meta.highlights` 少于 3 条或多于 6 条；某条缺 whatChanged / whyItMatters / impactOnYou。
15. `impactOnYou` 停在「值得关注」「可能会更快」这类空话，没落到具体用法或选型。
16. `source` / `url` 在输入里对不上，或者拼了一个像模像样的链接。
17. `techList` 少于 2 个，或术语没有翻译成人话。
18. 把「开源项目变多」「星标涨得快」说成「技术突破」。
19. 仓库部分推断成熟度、性能或采用情况（输入里没有这些信息）。
20. 语气变成营销话术：震撼、颠覆、炸裂、碾压、史上最强。

### D. 事实不合格（两个板块通用）

21. 出现输入里没有的具体模型名、版本号、参数、价格、benchmark 数字、论文结论、融资金额、公司动作。
22. 事实与推断混在一起，判断没有用「通常 / 大致 / 一般来说 / 值得关注 / 取决于」这类措辞点明。
23. 顺着动态标题往外推演输入里没有的细节。

### E. 朗读不合格

24. `script` 里有表情符号、括号注释、Markdown 标记（井号、星号、反引号、大于号、短横线）或网址。
25. `script` 里有阿拉伯数字（应写成「百分之十二点三」「二零二六年」这类中文读法）。
26. `script` 里有 body 里没有的事实。

### F. 一键体检

- `npx tsx src/server/llm/prompts/_check-ai.ts`：装配、提示词硬约束、样例 JSON 过 schema、长度与朗读适配全部自动核对，失败会打印具体条目并以非零码退出。
- 提示词 system 末尾的【收尾检查】是给模型自己过一遍的清单，人工复核时可以直接对着它逐条看。

## 五、维护提示

- 改契约（`src/server/llm/schema.ts`）后，**不需要改提示词**：输出骨架的字段清单是从契约推导的。但若新增的是必填字段，请同步在 `_check-ai.ts` 的样例 JSON 里补上该字段，否则自检会报 schema.parse 失败。
- `_check-ai.ts` 里的样例 JSON 写得比契约「多几个字段」（例如课程样例额外带了 `lessonTitle`、`goal`、`prerequisite`）：契约里没有的字段会被 zod 裁掉，不影响解析；这样契约收紧或改字段名时，样例仍能通过，起到缓冲作用。
- 两个提示词的 `temperature`：日课 0.6（要讲得生动），周报 0.5（要克制、稳）。`maxTokens`：日课 6000，周报 5000。
