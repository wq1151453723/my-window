从哪儿看起　本讲机制作用在你发出的 POST /v1/chat/completions 上：请求头走网关鉴权，messages 与 system 被拼成上下文，stream 决定返回是整包还是 SSE 事件流。

  • · 鉴权与限流发生在网关层，模型还没开始算，报错在这一层说明请求根本没进模型。
  • · messages 会被拼成一条线性上下文，system prompt 通常被放在最前面并影响后续所有 token 的生成。
  • · stream 打开后返回的是 SSE 事件流，每个事件带一小段增量文本，总耗时不变但首字更早。

 

先说你看到的现象。同一段 messages，有时候几百毫秒就开始吐字，有时候要等好几秒才一次性返回一大段；有时候改一个字段，输出风格就变了；有时候报错信息很短，压根没提到模型。这些差异不是随机的，它们分别发生在一次调用的不同层。

大白话直觉：一次调用像寄快递。你先过门禁（鉴权），再把包裹按格式打包（请求体），快递员送到仓库（模型），仓库按你的清单逐件取货（逐 token 生成），最后要么整箱送到（非流式），要么一件件往外递（流式）。每一层出的问题，现象都不一样。

第一层是网关。请求头里的鉴权信息在这里被校验，同时做限流和路由。这一层不碰模型权重，只决定你有没有资格、该被送到哪个后端。所以鉴权失败、配额耗尽、限流这类错误，通常在模型开始计算之前就返回了，响应里也不会出现任何生成内容。值得注意的是，这一层还会做请求体大小和字段合法性检查，字段名写错时往往在这里就被拦下。

第二层是消息拼装。messages 是一个数组，每个元素带角色和内容。服务端会把它拼成一条线性上下文：通常是 system 在前，然后按顺序接上用户和助手的轮次。system prompt 在这里不是特殊魔法，它只是被放在最前面的一段文本，但因为模型是逐 token 看前文的，最前面的内容会影响后面每一个 token 的生成概率。所以改 system，往往改的是整段输出的基调，而不是某一句。

第三层是生成。模型不是一次性写出整段话，而是每次预测下一个 token，把它接到序列末尾，再预测下一个。伪代码大致是：while 未结束: 取当前序列 → 算下一个 token 的概率分布 → 采样一个 → 追加到序列。人话就是：每吐一个字，模型都要把前面所有字重新看一遍，所以上下文越长，单步计算通常越重。这解释了为什么长对话会变慢、变贵，也解释了为什么输出会飘：每一步都是概率采样，不是查表。

第四层是返回。stream 关掉时，服务端等整段生成完再一次性返回，你拿到的是完整结果。stream 打开时，返回的是 SSE，也就是服务器推送事件：一条长连接上，服务端把每个增量片段作为独立事件推回来，客户端逐条解析再拼起来。总生成时间没变，但首字出现得更早，所以体感更快。值得注意的是，流式下错误可能出现在流中间，而不是一开始就报。

锚点场景对照。你写的那行 POST /v1/chat/completions，请求头里的鉴权对应第一层网关；请求体里的 messages 和 system 对应第二层拼装；stream 字段决定第四层是整包返回还是 SSE 事件流；而模型逐 token 生成这件事，对应你看到的每个增量片段和最终结束标记。换句话说，你请求体里每个键，背后都挂着上面某一层的机制。

与本周动态的关联。本周有一条「OpenAI makes it much harder for attackers to extract how its latest AI models think」，讲的是厂商在收紧对模型内部信息的提取。它说明一个机制问题：模型内部的计算过程并不在 API 返回里，你拿到的只有 token 和少量元信息，所以想理解一次调用发生了什么，只能从请求和返回这两端去推断，这也正是本讲拆四层的意义。

边界与不确定性。不同厂商在网关行为、SSE 事件格式、system 的处理方式上并不完全一致，具体细节取决于服务商实现，本讲给的是通用分层，不保证每一层都按同样顺序发生。

现在你能解释：为什么同一个请求，有时卡在鉴权、有时卡在生成、有时卡在流的中途。
